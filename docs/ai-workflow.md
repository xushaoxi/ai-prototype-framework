# 工具无关的 AI 七步研发流程

本流程可用于 Codex、其他编码助手或人工研发；不依赖特定模型或在线服务。每一步产物都留在项目中，以便交接、回归和审查。

1. **澄清业务**：写清角色、目标、字段、状态、动作、边界与不可做事项。将「能归档」写成「使用中可归档，草稿不能直接归档」。输出模块需求和接受条件。
2. **建立规范**：在 business-specs 添加稳定需求 ID，写清字段类型、必填、状态和 from/to。标明真实权限与仿真的区别。先读现有模块，复用 T01 契约。
3. **收敛实现计划**：列出会改的定义、store/HTTP、页面扩展、测试和文档，明确跨层接口与验证命令。普通字段变更使用配置，复杂规则保留显式代码。
4. **先验证关键规则**：先增加能失败的领域/HTTP或脚本测试，确认失败原因正确；再实现最小变更，转绿后整理。禁止通过删断言、放松类型或绕过 HTTP 掩盖失败。
5. **实现可演示界面**：覆盖查询、表单、详情、合法和非法操作、加载、空态、错误重试、持久化。每次新增定义同时更新规范和验收映射。
6. **运行双质量关口并审查**：第一关 `npm run verify` 检查规范、类型、lint、领域、HTTP、脚本与构建；第二关 `npm run test:e2e` 检查真实浏览器。查看桌面/移动截图和控制台，逐需求审查，修复再测。
7. **形成可交接证据**：运行 `npm run deliver`，提交源码、规范、实际日志和交付清单。记录未覆盖路径、演示局限、浏览器/Node 版本和复现步骤。未运行或跳过的项目明确标为未验证。

## 给 AI 的任务模板

```text
阅读 README、AGENTS、相关业务规范与已有测试。
目标：<模块 + 触发条件 + 期望结果>。
范围：<允许修改的文件/层>；不包含：<明确边界>。
验收 ID：<已有或新增的稳定 ID>。
先复现并写失败测试，再实现；同步规范与文档。
执行 verify 与适用浏览器路径，报告实际结果、文件与剩余限制。
```

不要将长聊天记录当作唯一规格；将已决定内容归档到规范和文档。AI 的自述不能代替实际命令结果，也不能代替对界面和业务边界的独立检查。
