# 工具无关的 AI 七步研发流程

本流程可用于 Codex、其他编码助手或人工研发；不依赖特定模型或在线服务。每一步产物都留在项目中，以便交接、回归和审查。

1. **澄清业务**：写清角色、目标、字段、状态、动作、边界与不可做事项。将「能归档」写成「使用中可归档，草稿不能直接归档」。输出模块需求和接受条件。
2. **建立规范**：在 business-specs 添加稳定需求 ID，写清字段类型、必填、状态和 from/to。标明真实权限与仿真的区别。先读现有模块，复用 T01 契约。
3. **收敛实现计划**：列出会改的定义、store/HTTP、页面扩展、测试和文档，明确跨层接口与验证命令。普通字段变更使用配置，复杂规则保留显式代码。
4. **先验证关键规则**：先增加能失败的领域/HTTP或脚本测试，确认失败原因正确；再实现最小变更，转绿后整理。禁止通过删断言、放松类型或绕过 HTTP 掩盖失败。
5. **实现可演示界面**：覆盖查询、表单、详情、合法和非法操作、加载、空态、错误重试、持久化。每次新增定义同时更新规范和验收映射。
6. **运行双质量关口并审查**：第一关 `npm run verify` 检查规范、类型、lint、领域、HTTP、脚本与构建；第二关 `npm run test:e2e` 检查真实浏览器。查看桌面/移动截图和控制台，逐需求审查，修复再测。
7. **形成可交接证据**：运行 `npm run deliver`，提交源码、规范、实际日志和交付清单。记录未覆盖路径、演示局限、浏览器/Node 版本和复现步骤。未运行或跳过的项目明确标为未验证。

## 给 AI 的任务模板

```text
阅读 README、AGENTS、相关业务规范与已有测试。
目标：<模块 + 触发条件 + 期望结果>。
范围：<允许修改的文件/层>；不包含：<明确边界>。
验收 ID：<已有或新增的稳定 ID>。
先复现并写失败测试，再实现；同步规范与文档。
执行 verify 与适用浏览器路径，报告实际结果、文件与剩余限制。
```

不要将长聊天记录当作唯一规格；将已决定内容归档到规范和文档。AI 的自述不能代替实际命令结果，也不能代替对界面和业务边界的独立检查。

## 从明确需求生成可运行原型：统一接入契约

用户提交需求，AI负责按规则选结构、组合共享代码、实现仿真和生成可运行原型。工作台用于浏览、操作和对照规则。输入不用预先写成组件配置，也不要求用户逐项决定普通布局。

### 读取与选择

先读本文件、README、AGENTS、[架构](architecture.md)，再按需读取：

| 需要决定 | 依据与入口 |
| --- | --- |
| 页面与能力如何分层 | [工作台建设方案](design/prototype-workbench-blueprint.md)，九族是候选检索入口，未实现项不是可用接口 |
| 查询、表单、容器和交互规则 | [设计指南](design/design-guidelines.md)，保留PAGE-003、FORM-007/008及已确认的桌面三列默认 |
| 颜色、密度、间距与布局 | [视觉基线](design/design-system.md)、src/core/theme.ts统一导出Ant主题和CSS变量；新页不得逐页另造主题 |
| 常规列表、录入和详情 | src/core/ui/LedgerPage.tsx、RecordForm.tsx、RecordDetail.tsx；模块定义经registry接入 |
| 控件及专用组合接口 | [复用指南](backend-pattern-reuse.md)及相应导出类型；不能只根据示例名称假定可复用 |
| 领域约束和验收 | 相关business-specs、src/mocks/store.ts、core/api.ts和对应测试 |

先输出一张简短映射表：需求/页面/主体结构/组合能力/字段与动作/容器/规则ID/例外/验收。对缺失规则作有依据的显式决定并归档；仅对改变产品目标的歧义询问用户，普通选择自主执行。无法合理匹配既有结构时说明扩展点，不硬塞进九族。

### 实现与产物

1. 根据交付要求选择独立项目或当前模块。独立项目沿用create:project脚本，禁止覆盖已有路径。
2. 常规T01修改definition与业务规范，注册模块；复杂嵌套对象或流程使用有限类型化扩展，不强制补造金额、部门等无关字段，不无限扩张配置解释器。
3. 数据和状态流转由store管理，经HTTP/MSW调用；表单局部输入和导航现场属于UI状态。明确演示身份、文件元数据等仿真边界。
4. 复用页面与组合实现；业务代码负责内容与规则。新需求不复制整页，不通过逐页CSS补丁营造统一外观。
5. 提供可运行源码、需求映射、启动/预览入口、实际验收日志及未覆盖事项。独立业务原型仅展示选定业务菜单和必要演示入口，工作台参考目录、旧业务样例和维护工具不能自动成为新业务菜单。

### 验收不能省略的两类证据

能力覆盖按本批承诺检查必要操作、状态和恢复；跨需求复用另行检查，二者不能互相替代。

- 核心流程：查询第二页→详情→编辑保存→关闭返回；保留合理的筛选、分页和现场，数据更新一致；失败保留输入；直接访问有有效返回路径。
- 差异复用：使用字段类型、关联和操作有实际差异的需求，记录修改了哪些公共文件、有无整页复制、临时样式或无关业务依赖。合成需求必须标明，不能代替真实用户场景证据。
- 交付检查：从干净目录运行产物，检查仅包含选定业务入口；verify、e2e、桌面与手机截图、控制台和deliver以实际结果记录。共享容器单测通过不等于新项目已生成或交付。

当前可用边界：T01生成器提供确定的模块创建路径；其他复杂模式的接口以实际代码为准。排程、关系图和可配置布局已有有限演示及共享接口，实际覆盖以能力矩阵为准；未实现的专用扩展不能标记为已落地。每轮验收应更新实际能力、例外及剩余差距。

规则定位：使用#/design-guide?rule=规则ID精确打开规则；示例侧可从适用规则或台账对照面板反查。状态、覆盖能力、未覆盖、证据与示例入口均在规则正文维护，应用索引只解析引用，不复制规则内容。
