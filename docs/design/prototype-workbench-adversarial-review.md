# 原型工作台建设方案：多角色对抗审查

日期：2026-10-29。审查对象：[建设方案](prototype-workbench-blueprint.md)。

状态：方案审查结论；已依据审查及用户答复修订方案正文，未修改运行界面或业务数据，未执行运行测试。本次证据来自用户已表达的目标、方案和现有源码，不能代替界面体验或新项目复用实验。下文问题行号对应审查时版本，修订后可按章节与标题定位。

## 1. 结论

现方案已纠正按业务名称堆叠模板的方向，但不能称为最优，也不能据此宣称已经完全理解用户。建议保留四层体系和任务导向入口，补齐使用契约、选型边界及复用证据后实施；不再按页面数量扩建。

“更优”的判断依据应是：新需求能否更快产出可运行原型、默认风格是否一致、是否容易查找和理解、是否避免复制整页、跨页任务是否成立，以及维护成本是否可控。目前没有比较实验或完整的新需求接入证据，不能作最优承诺。

## 2. 对目标的理解及证据强度

| 判断 | 依据与状态 |
| --- | --- |
| 建设对象是原型工作台与设计指南，不是资产管理等业务系统 | 用户明确说明“资产台账也只是一个组件库，并不是真实的实际业务” |
| 面向后续后台管理系统，需求明确后能据此绘制原型并保持产品风格一致 | 用户多次明确提出，属于核心目标 |
| 同一结构不因业务名称不同而增加菜单 | 用户直接质疑资产/供应商、高级表格、待办/审批等重复入口 |
| 指南应与可操作组件、页面效果一起查看 | 用户明确要求把指南放进工作台；应保留并排对照能力 |
| 不应逐项等待用户批准所有普通实现选择 | 用户明确要求先给整体内容，再持续做完 |
| 标准查询遵守PAGE-003，完整表单桌面默认三列，菜单不深嵌套 | 已有明确选择，应作为本轮基线保留 |
| 主要由AI读取指南和代码、产出新的可运行原型 | 审查过程中用户已明确确认：“把需求交给 AI，由它按指南和共享组件生成可运行原型” |
| 新业务原型默认独立项目，工作台作为长期参考 | 现有项目脚本支持这种方式，但它还不是用户已明确的默认选择 |
| “完整”指常见结构、组件、交互及组合的覆盖 | 与上下文一致；具体支持范围、专用扩展和交付格式仍须写明，不能解释成覆盖所有未来业务 |

使用方式已经确认，核心应落在AI接入契约、共享实现和可运行产物。工作台让用户查看效果与规则，也让AI找到正确接口；不把自定义工作台样例误当成整个产品的拖拽生成能力。独立项目或工作台内模块的落地位置可按实际交付要求选择，不需要因此暂停本轮方案审查。

## 3. 审查方法与交叉质询

三组独立只读审查分别从产品目标与使用者、交互分类与设计系统、架构复用与验收证据提出反例。主审核对关键源码和方案段落，再要求前两组为现方案作反方辩护，检查修正是否会制造过度建设。

| 角色挑战 | 反方辩护 | 主审裁定 |
| --- | --- | --- |
| 产品：展示目录不等于需求到原型的产出路径 | 不一定需要新增生成界面，操作契约和完整实例就能验证AI代码组合路线 | 接受缺口；用户已确认AI代码组合，补操作契约与实例 |
| 交互：九族存在重叠，选型可能不一致 | 检索入口可以重叠，配置向导也可以复用分步表单 | 不推倒分类；区分入口、主体结构和可选能力，不要求互斥实现 |
| 架构：注入服务不等于换数据结构仍可复用 | 现方案已经要求有限接口，不必先造通用配置引擎 | 接受风险；用真实结构差异驱动容器、内容插槽和回调提取 |
| 测试：两个样例不能证明所有能力都完成 | 也不应给每族机械凑两套业务、先铺完所有复杂测试 | 分开验证能力覆盖与跨项目复用；按适用范围记录证据 |
| 使用者：业务样例可能继续污染新项目 | 当前创建项目脚本可以复用，不必另造导出系统 | 规定新项目包含内容，并实际检查一次干净产出 |

## 4. 优先问题与可检查的修正

### P1：没有完整的需求到原型使用契约

证据：[方案第8行](prototype-workbench-blueprint.md:8)、[第178行](prototype-workbench-blueprint.md:178)讲了目标和映射步骤，却没有明确执行者、必读入口、改动位置、预览和最终产物；[复用指南第27行](../backend-pattern-reuse.md:27)明确生成器只支持T01。

风险：得到一个更大的示例展厅，每次新需求仍靠AI重新理解目录、手工拼接。

修正：按用户已确认的AI代码组合方式，提供一条实际可执行的流程，包含需求摘要、规则索引、选型映射、稳定共享出口、业务适配位置、预览和交付步骤。无需为此额外开发拖拽生成器。

验收：从一份新需求和干净项目目录开始，产出可运行原型；记录公共代码修改、复制整页、临时样式以及无关示例残留。不能只展示现有样例。

### P1：页面分类可用于检索，但还不是充分的选型规则

证据：[表单](prototype-workbench-blueprint.md:52)与[配置向导](prototype-workbench-blueprint.md:94)都有分步能力，[第181行](prototype-workbench-blueprint.md:181)要求每页匹配九族；[第72行](prototype-workbench-blueprint.md:72)还将不同时间模型绑定为同一组任务。

修正：九族保留为当前候选入口，增加“主任务、主体结构、可选能力、适用/不适用”的简短判据。共享分步能力不要求两个入口合并；日历事件、层级任务、资源占用也不强制使用一个业务模型。无法合理归类时，先判断现有组合能否承载，再说明是否需要显式扩展。

验收：给一份无预设菜单的需求，能解释为何选该结构、为何不选相邻结构；不能靠修改业务名称证明新增结构的必要性。

### P1：现有复用接口仍带有固定业务，验收安排过晚

证据：[PatternService](../../src/core/patterns/service.ts:4)强制完整快照；[PatternSnapshot](../../src/core/patterns/types.ts:13)同时绑定组织、角色、审批等域；[AdvancedRecordForm](../../src/app/patterns/FormPatterns.tsx:9)使用固定payload，[表单字段](../../src/app/patterns/FormPatterns.tsx:77)固定申请名称、采购类别、部门和金额。[实施批次](prototype-workbench-blueprint.md:193)把复用验收放在复杂模式补齐之后。

这是现有基线与未来复用承诺之间的距离，不是说方案已声称完成这些改造。

修正：先用一条纵向新需求验证共享容器、类型化内容和提交回调，再扩展复杂模式。原业务快照作为样例适配，不成为所有新项目的必需数据。共享实现只提取实际需要的差异，不建设任意字段解释器。

验收反例：设备申请与培训报名可作为合成试验，后者有参与者数组和场次、没有金额。接入不得要求补造采购字段、引入整套组织/审批快照，或复制整页。此为审查用合成场景，不是用户新需求，不新增业务菜单。

### P1：单页能力之外，缺少跨页任务的共同契约

证据：[详情返回](prototype-workbench-blueprint.md:62)、[关系图现场](prototype-workbench-blueprint.md:80)、[指标下钻](prototype-workbench-blueprint.md:86)分别提出要求，[第184行](prototype-workbench-blueprint.md:184)尚未规定它们组合后的上下文和更新责任。

修正：明确来源条件、对象身份、返回落点、未保存处理、保存后的更新和焦点恢复。沿用现有工作台现场机制，增加有限约定，不引入工作流引擎。

验收：筛选列表第二页→详情页签→关联对象→编辑保存→返回，原筛选、分页、选中项和现场合理保留，修改可见；直接打开详情也有有效返回路径。另验录入中新增关联对象后返回并回填，避免丢失主表单。

### P2：一致性与完整性需要明确边界和证据

证据：[方案第147行](prototype-workbench-blueprint.md:147)要求单一主题，但[视觉基线第7行](design-system.md:7)与[当前Ant主题](../../src/main.tsx:16)的次要文字、边线值并不一致；[第191行](prototype-workbench-blueprint.md:191)未给各模式的适用状态和证据清单。

修正：统一语义token及Ant主题/CSS的消费来源，确定存量迁移边界；对每项标识“计划、可演示、可复用、已验证”。能力清单注明必要操作、适用状态、仿真边界、延期项与例外。不同颜色若确有不同语义，可保留并明确命名，不机械合并所有值。

验收：主题入口变化能一致影响代表性查询、表单、详情；新页面不靠逐页覆盖修补默认风格。复杂图形交互提供可执行的键盘或按钮等价操作。检查本批承诺的能力与恢复行为，不能用旧模板路由数量或测试总数代替覆盖证据。

## 5. 建议保留、调整及不额外建设的内容

保留四层内容、规则与实例对照、PAGE-003、表单容器选择和桌面三列基线、浅层导航，以及复杂结构的整体目标清单。九族用于找模式，组件层负责真正共享；二者不是同一份继承结构。

调整实施顺序：明确使用契约→整理导航和重复内容→以差异化新需求验证主题及核心容器→据结果提炼接口→补齐复杂结构和组合→按支持范围记录覆盖与复用证据。复用验证贯穿建设，不等所有页面做完才开始。

不因本次审查额外建设低代码平台、通用业务引擎、自动调度算法或完整权限后台。保留广泛结构覆盖目标，但区分可工作的演示闭环、确定性仿真和专用扩展；尚未实现或验证的内容如实标明。

## 6. 能说与不能说的结论

- 可以说：已经明确用户反对的方向、必须保留的设计基线和工作台的主要价值；现方案具备可继续收敛的结构。
- 不能说：九类足够覆盖所有未来后台；已有示例已证明异构业务复用；现有测试通过证明建设方案适用；未来产品风格会自动绝对一致。
- 下一次可信判断应来自：一份独立新需求的产出过程、可检查的共享边界、代表性跨页流程，以及用户对实际产物的反馈。
